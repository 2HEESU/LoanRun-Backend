# 실제 월·누적 실적 기반 계획 성과 조회

Issue #138의 `PlanPerformanceQueryService.current(user,loan)`은 실제 원천, 저장 계획 일정,
명시적 월 관측 근거, 기존 정기 상태와 성과 계산기를 연결하는 내부 조회다.
HTTP·공통 포트·DB·환경변수·의존성 변경은 없다. READ_ONLY/REPEATABLE_READ이며 상위 트랜잭션이
있으면 상위 격리 수준이 적용된다. 금융 원본·계획·revision을 쓰지 않는다.

## 기간과 확인 근거

- 현재월은 max(효력일,월초)~기준일, 누적은 효력일~기준일이다. 전체 loan-month 확인 근거를
  검증한 후 실제 원천을 그 계획의 부분월 범위로 잘라 합산한다. 효력일 이전 납부는 제외한다.
- 납부 완료와 BULLET 적립 완료는 독립적이다. 해당 기간의 모든 관련 loan-month가 확인되어야
  그 지표의 누적 실적을 공급한다. 현재월이 확인돼도 이전월이 미확인이면 누적은 null이다.
- 기준일 이후 실제 행은 합산하지 않는다. 확인용 월 전체 원천과 기준일까지의 행 수·관련 원금/
  적립 합계가 일치해야 하므로 미래 행을 포함한 확인 근거도 조용히 사용하지 않는다.
- 실제 확인 공급자가 없으면 월별 확인 조회를 반복하지 않고 확인 실적은 null이다.
  누적 범위가1200개월을 넘으면 일부 기간만 확인하고 전체 완료라고 선언하지 않는다.

monthlyRecorded/cumulativeRecorded는 저장된 행의 사실만 별도 보존한다. 빈 범위의 raw0은
기록 합계일 뿐 confirmed actual0이 아니다. 성과의 actual/gap은 근거가 없으면 null이다.
확인된 빈 원장만 실제0으로 비교할 수 있다. 깨진 공급자·overflow는503이며 정상 빈 관측이 아니다.

## 일정·진행률·정기 상태

PlanScheduleProjection과 PlanPerformanceCalculator를 재사용한다. V2처럼 원래 약정이 없으면
과거 목표를 현재 약정으로 대체하지 않는다. 확인된 실적은 독립적으로 남을 수 있으나 계획 근거가
없으면 gap/track을 만들지 않는다. 실제 원금 진행률도 계속 null이다. 월 근거와 효력일 이후 원금
합계만으로는 시작 잔액을 캡처한 정확한 시각 이후의 감소를 입증할 수 없다. 같은 날짜 내 기록 순서/
잔액 보정 근거가 필요하며 잔액 차이나 Actuals.principal을 PrincipalActual로 자동 대체하지 않는다.

정기 상태는 StoredDueQueryService를 재사용한다. 기간 내 UNRECORDED가 있으면 미기록을 먼저
알리고, 그 외에는 날짜순 첫 미충족 저장 회차를 표시한다. 모두 충족했으면 현재월의 마지막 저장
회차가 있을 때만 PAID를 표시한다. 지난 월의 PAID를 현재월 완료로 연장하거나 없는 회차를 만들지
않는다. UNPAID/PARTIAL은 추가 목표 상태와 구분한다.

BULLET은 초기 자산을 월 적립 실적으로 넣지 않는다. 납부 확인이 없어도 독립적으로 확인된
적립 실적은 비교할 수 있다. 원금 진행률을 적립률로 채우지 않는다.

## 조회 상태와 한계

미적용 계획은 원래 일정과 NOT_EFFECTIVE를 남기고 실제 성과0을 만들지 않는다. 비활성은 INACTIVE,
원천 부재는 NO_APPLICABLE_PLAN이다. AVAILABLE은 조합 성공을 뜻하며 모든 성과가 확인됐다는 뜻이
아니다. 계획 원천 테이블 부재는503이다. 테스트 DB만 SQL proposal을 사용한다.
현재/시작 약정의 상환 방식이 다르면 과거 지표를 혼합하지 않고 실패한다. 조회 중 기준일이 달라진
정기 상태도 실패시켜 재조회를 유도한다. 과거 as_of 재구성·월 override·시작 원금 이후 실제 감소 근거·
확인 저장 workflow·HTTP/공통 포트·실제V4 적용은 후속이다.

실제 PostgreSQL 원천 → 월 관측 검증 → 원래 일정 → 성과 계산으로 부분월·미확인 누적·0원·1원,
정기 상태·BULLET·미래/변경 원천·소유권·원본 불변·금액 경계를 검증한다.
