# 상환자금 적립 등록 — API #33

`POST /api/repayment-savings/`는 익명 세션 소유자의 활성 BULLET 대출에 실제 적립 장부 기록을
추가한다. FREE/PRO 공통이며 마지막 슬래시가 필요하다. 실제 송금·원금 납부가 아니다.

요청 JSON은 loan_id(양의 Long), saved_at(실제 YYYY-MM-DD), amount(1 이상 Long) 세 필드만 받는다.
Idempotency-Key는 1~128자, 필수다. 최신 잔액 스냅샷 날짜 이상부터 KST 오늘까지 입력할 수 있다.
같은 날짜의 수정 가능 경계는 기존 납부/적립 조회와 동일하다. 소수·문자열 금액, 명시 null,
미래 날짜, 비활성/분할 대출, 추가 필드는 거절한다.

- 성공: 201 SAVING_CREATE_SUCCESS, `상환자금 적립 기록 성공`.
- 해석 가능한 JSON의 입력/키 오류: 400 SAVING_VALIDATION_ERROR,
  `만기일시상환 적립 입력값을 확인해 주세요.`. JSON 파싱·미디어 타입 오류는 공통 처리기를 따른다.
- 다른 사용자/없는 대출: 404 SAVING_NOT_FOUND, `리소스를 찾을 수 없습니다.`.
- 같은 키의 다른 본문, 등록으로 생기는 표현 범위 초과: 409 SAVING_CONFLICT,
  `적립 잔액 또는 이미 사용된 금액과 충돌합니다.`.
- 필수 실제 예산 재계산 공급자 부재: 503 SERVICE_UNAVAILABLE, 저장 없음.

## 트랜잭션 및 응답

공통 IdempotencyService가 사용자 잠금/본문 해시/저장 응답을 관리한다. 사용자 잠금 후 해당 소유자의
대출 행을 잠그고 입력·잔액을 검증한다. 기존 V2 repayment_savings에 삽입 → 실제 적립일의 월부터
BudgetRecalculationPort 재계산 → RevisionPort 한 번 증가 → 기존 적립 조회로 응답 계산 →
201 응답 저장을 한 트랜잭션으로 처리한다. 어느 단계든 실패하면 전체 롤백된다.

저장된 같은 키/본문은 이후 대출 상태·기준일·스냅샷·예산 의존성 변화보다 우선하여 최초 201 응답을
재사용한다. 같은 날짜/금액이어도 다른 키면 별도의 실제 기록으로 저장한다. 키 범위는 사용자,
POST, 정확한 /api/repayment-savings/ 경로다. 실패한 키를 성공 응답으로 예약하지 않는다.

응답 saving은 실제 새 기록이며 나머지 자산·필요/예정 적립액·당월 기록 합계·진행률은 기존
GET과 같은 계산을 사용한다. 과거 월에 적립해도 actual_saving_amount는 응답 시점의 당월 기록 합계다.
report_stale=true는 실제 금융 입력 revision 변경을 나타낸다. 적립만으로 대출 잔액·상태·이자·확정 회차,
실제 납부·배분, 초기 자산, 저장 계획을 변경하지 않는다. 관측 완료나 실제 0원 확인을 생성하지 않는다.

현재 구현은 양수 기록 추가다. 기존 자산 일자별 음수/overflow를 점검하고, 새 적립을 포함한
전체 일자별 잔액도 확인하므로 나중 사용으로 낮아진 최종 잔액만 보고 과거 overflow를 놓치지 않는다.
양수 추가는 어떤 기존 거래 순서에서도 잔액을 줄이지 않는다. 입출금 선후를 새로 정하거나
기존 사용 기록을 재배정하지 않는다. 독립 테이블의 같은 날 거래 선후에 대한 읽기 모델 한계는
[적립 조회](SAVING_LIST.md)와 같다. 오류 원장을 자동 복구하는 기능은 아니다.
후속 납부/적립 수정·삭제에서는 감소 거래의 순서·중간 잔액·이미 사용한 자산 검증이 별도로 필요하다.

## 실제 연동 상태

중앙에는 BudgetRecalculationPort 실제 구현이 아직 없다. 정상 입력도 503으로 종료하고 적립/키/revision을
저장하지 않는다. 테스트용 공급자는 성공/실패/롤백 계약 검증에만 사용하며 운영에 등록하지 않는다.
이 API 구현 완료와 실제 예산·정산·이월 연동 완료는 구분한다. DB/Flyway/환경변수/공통 계약/의존성
변경은 없다. V2만 사용하며 팀원 2의 위험 이력 SQL proposal을 활성화하지 않는다.
