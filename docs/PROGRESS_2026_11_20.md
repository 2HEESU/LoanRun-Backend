## 보존 및 검증

- 계획은 미리보기 token/revision 재검증 후 새 버전을 append한다. 원래 계획·당월 override·실제 납부를 덮지 않는다.
- 납부는 실제 날짜/ID 순 재처리하며 실제 구성, 최신 잔액 보정, 확정 회차를 보존한다. 원금/이자/비용/정기/추가/적립을 분리한다. 실제 0원과 미기록을 구분한다.
- 완납 취소에 필요한 미확정 회차는 삭제 전 보존하고 같은 실제 ID/원래 필요액/이자로 복원한다. 현재 잔액으로 과거 의무를 만들지 않는다. 부분 의무를 남긴 채 완납으로 표시하지 않는다.
- 사용자/대출 잠금 아래 원본·파생 배분/잔액·미래 회차·예산·revision·멱등 응답을 한 트랜잭션으로 처리한다. 실패는 전체 롤백, 같은 값 수정은 금융 재계산/revision 변화 없음이다.
- Java 21 clean build: **742개 테스트, 실패/오류/건너뜀 0**. 정상/입력/소유권/PRO/stale/멱등/날짜·원금·수수료·자산 경계/완납 취소/원약정 복원/실패 롤백을 포함한다. 최종 CI·머지 상태는 PR 기록에서 확인한다.

## 아직 필요한 운영 연결·협업

- 실제 예산 조회/재계산, 전략 후보 및 과거 목표/월초 잔액 등 Team 2 공통 공급자의 중앙 통합이 필요하다. LoanQueryPort/PlanQueryPort/PlanPresentationPort의 전체 계약 어댑터도 DB baseline과 함께 연결해야 한다. 부분 구현을 공통 포트로 조기 설치해 기존 V2 동작을 깨지 않는다.
- V3/V5 실제 개발 DB 상태는 아직 확인되지 않았다. V4 계획 버전, plan_application_events, payment_due_archives SQL은 **제안/격리 테스트용**으로만 추가했으며 Flyway/실제 DB에 활성화하지 않았다. 기존 checksum/적용 이력은 수정하지 않았다.
- 명시적 납부/적립 관측 완료 공급이 없어 런타임 미확인 실적·비율은 null이다. 건수/회차 PAID를 월 전체 완료로 추측하지 않는다.
- 생성되지 않은 미래 회차는 가짜 ID나 빈 계약 일정으로 반환하지 않고503이다. 저장된 다음 회차는 납부 재처리에서 갱신/복원한다. 과거 약정/잔액을 증명할 수 없는 조회·정정도 null/503/409로 보호한다.
- 실제 DB 적용/공급자 연결 후 시연 데이터로 통합 검증·배포가 필요하다. 이번 작업에서 배포/main 반영/인프라 생성/비용 발생 작업은 하지 않았다.
