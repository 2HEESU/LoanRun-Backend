# 대출 삭제 — API #17

`DELETE /api/loans/{loan_id}/`는 익명 세션 소유자의 대출을 DELETED로 보존한다.
본문 없음, 마지막 슬래시 필수이며 FREE/PRO 공통이다. 상세 명세에 필수 멱등 키가 없으므로
Idempotency-Key 없이 사용할 수 있다. 제공하면 기존 공통 멱등 응답을 선택적으로 사용한다.

- 200 LOAN_DELETE_SUCCESS, `대출을 삭제했습니다.`. data는 loan_id/deleted=true/status=DELETED다.
- 타인/없는/이미 DELETED 대출은 동일404 LOAN_NOT_FOUND, `대출을 찾을 수 없습니다.`.
- REGULAR/EXTRA 구분 없이 실제 납부가 한 건이라도 있으면409 LOAN_HAS_PAYMENTS,
  `상환 내역이 있는 대출은 삭제할 수 없습니다.`. 원금 없는 이자 납부도 포함한다.
- 본문/잘못된 선택 키/path 숫자 변환 등은400 VALIDATION_ERROR의 공통 처리를 따른다.
- 키가 있는 최초 요청과 다른 본문은409 IDEMPOTENCY_CONFLICT다.
- 실제 예산 재계산 공급자가 없으면503 SERVICE_UNAVAILABLE이며 상태·revision·키를 저장하지 않는다.

## 원본과 상태

삭제는 loans.status와 updated_at만 변경한다. 원금·이자·금리/잔액 이력·초기 자산·적립·실제 납부·
배분·확정 회차·등록 기본 계획은 보존한다. DELETE를 실제 원금 상환이나 완납으로 계산하지 않는다.
실제 납부가 없다는 자격을 만족하면 PAID 대출도 보관 상태로 전환할 수 있다.

기존 대출 목록 ACTIVE/ALL, 활성 등록 한도 및 미래 엔진 대상은 DELETED를 제외한다.
일반 금리 조회도404다. 내부 원본/과거 적립 조회에는 보존한다. 저장 회차를 물리 삭제하지 않는다.
후속 일정·대출 조회 포트는 보존된 원본과 미래 활성 대상을 구분해야 하며 API #26을 이 PR에서
구현/검증했다는 뜻은 아니다.

## 원자 처리와 멱등성

사용자 잠금 → 본인 대출 행 잠금 → 해당 대출의 실제 납부 확인 → 상태 변경 → 현재 KST 월부터
예산 재계산 → revision1회 증가 → 응답(키 제공 시 재사용 응답 포함)을 한 트랜잭션으로 처리한다.
DELETE는 과거 실제 납부/적립을 지우지 않고 현재·미래의 활성 부담을 숨기므로 재계산 시작은
등록 월이 아닌 삭제 시점 월이다. revision 변경으로 기존 결과/전략 후보는 최신 입력과 구분한다.
실제 V4 저장 전략의 표시/재검토 연동과 전체 금융 포트 구현은 별도 후속 통합이 필요하다.

재계산 실패하면 DELETED 상태와 updated_at, revision 및 키 저장을 롤백한다. 원본은 물리적으로
삭제하지 않는다. 같은 사용자의 등록/납부/삭제도 공통 사용자 잠금을 따라야 한다.

키를 제공한 같은 요청은 이후 대출이 DELETED거나 기준일이 달라도 최초200을 재사용한다.
새 키/키 없는 반복 요청은 이미 보이지 않는 대출에 대한404이며 추가 변경은 없다.
키는 사용자/DELETE/해당 대출 경로별이다. 키 없는 동시 삭제도 사용자 잠금으로 한 번만 변경된다.
성공 응답 schema에 report_stale 등 새 필드를 임의 추가하지 않는다.

## 실제 연동 상태 및 검증

현재 중앙에 실제 BudgetRecalculationPort가 없으므로 유효한 운영 삭제는503/상태 보존이다.
테스트용 공급자는 운영에 등록하지 않는다. API 구현과 실제 예산·전략·리포트 통합/배포를 구분한다.
DB/Flyway/환경변수/공통 계약/의존성 변경은 없다.

실제 HTTP/PostgreSQL에서 네 상환 방식, 키 없는 삭제, 선택 키 재사용/충돌, 납부 종류별409,
원본·적립·기본 계획 보존, 목록 제외/활성 한도, PAID 보관, 현재 KST 월 재계산, 동시성 및 실패 롤백을
검증한다. 별도 예산 구현 없는 실제 구성에서는503/상태·revision·키 보존을 확인한다.
